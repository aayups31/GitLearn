# OutClass: the next useful release

Proposed priorities, October 11, 2026. These extend the working 0.4.2 preview; they are not claims about features already delivered. See [current scope](current-build.md) and the [full learning roadmap](learning-to-contribution-roadmap.md).

The next release should help a Udemy learner apply a concept before the course ends, then demonstrate it again with a changed requirement. Success means a working learner-owned result and an explanation of its decisions.

## 1. Validate the complete experience with real learners

Run a small voluntary beta across actual Python and JavaScript Udemy courses. Observe first installation, pairing, explicit source import, first successful run, restarting, a practical suggestion, and a task completed with guidance. Record setup obstacles, missing source context, confusing suggestions, useful hints, and the actual cost of optional AI. Collect only information participants explicitly agree to share; do not add silent telemetry.

Exit: learners can reach and resume their own working code, and observed usability failures have concrete fixes. Automated fixtures do not substitute for this gate.

## 2. Make during-course practice genuinely relevant

Add optional goals and a session time budget. Match a small reviewed task to imported lesson material, explicit prerequisites, and actual attempt evidence. Explain why this is a useful moment to practice. Offer Start, Later, and Choose another without blocking the course. Expand the six existing briefs into a reviewed catalog covering common Python/JavaScript course concepts before relying on unrestricted generation.

Exit: a suggestion fits the learner's available time and observed course context. Missing transcripts or prerequisites remain visible, and the engine does not equate watched lessons with skill.

## 3. Demonstrate transfer and improve teacher feedback

Follow a completed task with a reviewed variant: a changed requirement, a different input, or a new failure to diagnose. Ground hints in the learner's saved attempt, actual run results, and cited course passages. Preserve progressive help, clearly distinguish general programming advice from course-derived answers, and give concrete feedback about failing behavior. Add reviewed evaluation examples for tutor relevance, citation support, escalating hints, and complete-solution avoidance. Multi-file task checks must attribute evidence to all relevant saved files before claiming that a project revision passed.

Exit: the learner can solve a comparable variant with less help and explain the reasoning. Passing tests describe tested behavior; they do not certify mastery or industry readiness.

## 4. Connect a small project to responsible live work

Give one supported project a short user need, acceptance criteria, milestones, and a changed-requirement review. Improve open-source matching using recorded practical evidence, setup burden, current issue availability, and contributor rules. Guide baseline checks, reproduction, a learner-owned patch, and a local PR draft with real test evidence. Maintainer feedback should inform the next learning task. Public actions remain explicit learner choices.

Exit: one supported project and contribution journey reaches a useful reviewable result without the assistant doing or publishing the work for the learner.

## Expansion after this milestone

Choose the next learning platform from beta feedback. Finish tested upgrade recovery and signed Windows distribution, then consider additional operating systems and optional managed AI access. Coding-agent integrations remain deferred. The primary outcome measure is successful independent attempts and useful return sessions, with traceable evidence, rather than watch time, chat volume, or a fabricated readiness score.
